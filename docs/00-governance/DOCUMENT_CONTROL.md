# 文档控制规范

| 属性 | 值 |
|---|---|
| 文档编号 | GOV-002 |
| 版本 | 0.1.0 |
| 状态 | Baseline |
| 生效日期 | 2026-07-30 |
| 责任角色 | 项目负责人 |

## 1. 目标

保证项目决策、需求、设计、实现、验证和交付均可追踪、可复核、可重现。

## 2. 文档分层

1. **规范（`docs/`）**：描述当前必须遵守的规则和当前有效设计，可随版本受控演进；
2. **记录（`records/`）**：证明某次活动实际发生，合并后原则上不原地改写，只能补充更正说明；
3. **模板（`templates/`）**：创建记录的结构，不是执行证据；
4. **代码内说明**：模块 README、API 描述和必要注释，必须与实现一同变更。

## 3. 编号规则

| 对象 | 格式 | 示例 |
|---|---|---|
| 需求 | `REQ-YYYY-NNNN` | REQ-2026-0001 |
| 缺陷 | `BUG-YYYY-NNNN` | BUG-2026-0001 |
| 架构决策 | `ADR-NNNN` | ADR-0001 |
| 风险 | `RSK-YYYY-NNNN` | RSK-2026-0001 |
| 测试计划 | `TP-版本-序号` | TP-0.2.0-01 |
| 测试报告 | `TR-版本-序号` | TR-0.2.0-01 |
| 验收记录 | `UAT-版本-序号` | UAT-0.2.0-01 |
| 发布记录 | `REL-版本` | REL-0.2.0 |
| 事件 | `INC-YYYY-NNNN` | INC-2026-0001 |

## 4. 最低元数据

受控文档必须包含编号、版本、状态、最后更新日期和责任角色。过程记录还必须包含执行人/角色、执行时间、输入版本、环境、结果和证据链接。

## 5. 评审与批准

| 文档 | 起草 | 必要评审 | 批准 |
|---|---|---|---|
| 产品范围/需求 | 产品负责人 | 架构、测试、业务代表 | 项目负责人 |
| 架构/ADR | 架构负责人 | 开发、安全、运维 | 技术负责人 |
| 测试策略/报告 | 测试负责人 | 开发、产品 | 项目负责人或发布负责人 |
| 发布记录 | 发布负责人 | 测试、运维、安全 | 项目负责人 |
| UAT/验收结论 | 业务代表 | 产品、测试、运维 | 业务验收负责人 |

同一人可以兼任多个角色，但作者不能成为高风险变更的唯一批准人。

## 6. 变更与归档

- 规范通过 PR 变更，重大决策同时新增或替代 ADR；
- 已签署记录如需纠错，追加“更正”章节，保留原结论和修改原因；
- 发布证据至少保存到产品停止维护后两年，若合同或法规要求更长则从其规定；
- 外部流水线、工单和监控证据应保存稳定链接或导出摘要，避免链接失效后无法审计；
- 每季度检查失效链接、过期规范、未关闭风险和未完成复盘。
