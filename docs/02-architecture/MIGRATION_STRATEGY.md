# 上游组件迁移与复用策略

| 属性 | 值 |
|---|---|
| 文档编号 | ARC-002 |
| 版本 | 0.1.0 |
| 状态 | Baseline |
| 生效日期 | 2026-07-30 |
| 责任角色 | 架构负责人 |

## 1. 策略

采用绞杀者模式，按业务能力逐段接管，不进行全量 Python 重写，也不将所有原服务永久包装。

每个候选组件必须得到一个处置结论：

- `Keep`：源码完整、可构建、契约可控，直接作为目标组件维护；
- `Wrap`：短期有价值但边界/契约不理想，通过适配器过渡；
- `Rewrite`：业务边界稳定但组件不可维护，按契约重新实现；
- `Reject`：许可证、安全、缺失源码或价值不足，禁止进入产品。

## 2. 当前初步处置

最终结论以 P0 组件准入报告为准。

| 能力 | 初步策略 | 说明 |
|---|---|---|
| BKN/本体核心 | Keep/Wrap | 优先复用 Go 核心，隔离 API 和内部模型 |
| ontology-query | Keep/Wrap | 保留语义查询性能，补契约测试 |
| Vega 数据访问 | Keep/Wrap | 避免 Python 重写连接和大查询链路 |
| Context Loader/检索编排 | Wrap/Select | 复用算法与测试，纳入统一知识领域模型 |
| Native Metrics | Select | 先验证与指标中心目标模型的重合和差距 |
| Dataflow 可构建部分 | Select | 仅纳入试点需要的接入与解析能力 |
| TraceAI 采集 | Select | 纳入统一可观测方案前评估协议与维护性 |
| SDK/Admin | Rewrite/Consolidate | 保留成熟测试用例，统一生成客户端、认证和配置 |
| 缺失源码的发布服务 | Reject/Replace | 没有可验证源码和许可证不得成为核心依赖 |
| 现有 LLM 情景预测 | Wrap as narrative | 只能作为叙述辅助，不能冒充统计预测引擎 |

## 3. 组件准入清单

每个组件进入主干前验证：

1. 精确来源、提交 SHA、标签和变更历史；
2. 源码、构建脚本、测试、数据库迁移和部署清单完整；
3. 本地/CI 可重现构建，基础镜像可追溯且使用摘要；
4. 单元、集成、契约和最小烟雾测试结果；
5. 许可证、NOTICE、传递依赖、修改和分发义务；
6. CVE、密钥、默认凭据、日志敏感信息和网络暴露；
7. API、数据模型、认证、租户和错误语义；
8. 性能基线、资源消耗、可观测性、备份和恢复；
9. 维护者、替代方案、退出成本和预计寿命；
10. Keep/Wrap/Rewrite/Reject 结论及批准人。

## 4. 迁移步骤

### Wave 0：冻结和盘点

- 固定所有上游提交 SHA，生成源码清单、SBOM 和许可证清单；
- 建立可重复构建和最小运行基线；
- 记录缺失源码、外部镜像和默认配置风险；
- 输出组件处置矩阵。

### Wave 1：建立防腐层

- 统一身份、请求上下文、追踪、错误和 OpenAPI 契约；
- 为语义引擎、数据引擎和对象存储建立端口；
- 使用生成客户端和契约测试连接保留组件；
- 禁止新业务直接调用旧服务。

### Wave 2：业务纵向切片

先完成“一个数据源—一个指标—一个驾驶舱—一个分析事项—一个决策”的端到端链路，再扩展功能宽度。

### Wave 3：知识与分析

建立统一知识库领域模型和 ACL，复用可用的解析/检索能力；独立建设可回测预测，不混用 LLM 叙述与数值预测。

### Wave 4：替换与收敛

依据调用量、故障、维护成本和源码风险，逐个替换过渡服务。每次替换必须减少一个明确依赖或部署单元。

## 5. 替换门禁

只有同时满足下列条件才允许下线旧组件：

- 新旧契约映射完整，兼容期和消费者清单明确；
- 对账、回放或影子流量证明结果达到阈值；
- 性能、容量、安全和故障注入测试通过；
- 数据迁移已演练，备份和回滚有效；
- 监控可区分新旧路径并完成观察窗口；
- 责任人批准，旧数据、密钥和基础设施按记录退役。

## 6. Python 重写判定

满足以下多数条件时才考虑将某 Go 能力重写为 Python：源码/构建不可持续；边界和行为已稳定；完整契约与回归样本存在；Python 性能和内存达到基线；能实际移除一个部署单元；团队能够承担长期所有权。

“语言统一看起来更整洁”不能单独成为重写理由。
