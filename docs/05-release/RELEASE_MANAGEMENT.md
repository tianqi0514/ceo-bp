## 1. 版本规则

产品使用语义化版本 `MAJOR.MINOR.PATCH`：

- MAJOR：用户/API/数据存在经批准的不兼容变化；
- MINOR：向后兼容的新能力；
- PATCH：向后兼容的修复；
- 预发布：`-alpha.N`、`-beta.N`、`-rc.N`。

产品版本统一引用各制品的不可变版本和摘要，不要求所有内部组件使用同一版本号。

## 2. 分支与制品

- `main` 始终保持可发布；
- 使用短功能分支和 PR，不维护长期功能分支；
- 发布候选由受保护标签/流水线从主干产生；
- 同一制品从测试环境提升到生产，禁止生产临时重建；
- 镜像、包、迁移和 OpenAPI 均关联提交 SHA、构建号、SBOM 和签名/校验和。

## 3. 发布流程

1. 产品冻结版本范围和追踪矩阵；
2. 构建候选制品并生成 SBOM、变更和迁移清单；
3. 完成测试报告、安全/许可证检查和缺陷评审；
4. 在 staging 演练部署、迁移、烟雾和回滚/恢复；
5. 业务执行 UAT 并签署结论；
6. 发布负责人召开 Go/No-Go，记录参与人、证据和遗留风险；
7. 在批准窗口发布，执行生产烟雾和关键指标观察；
8. 观察窗口通过后关闭发布；失败则回滚或前滚修复；
9. 更新 `CHANGELOG.md`、发布记录、运维知识和复盘。

## 4. Go/No-Go 门禁

- 需求范围和追踪矩阵完整；
- 测试准出，阻断缺陷为零；
- 安全、隐私、数据和许可证无未批准高风险；
- 数据迁移、备份、恢复和回滚演练通过；
- 容量、SLO、告警、值守和用户通知就绪；
- UAT 已通过或明确说明为何不适用；
- 制品不可变且来源可验证；
- 每项已知风险都有责任人、缓解措施和到期日。

## 5. 数据库和 API 兼容

数据库采用 Expand → Migrate → Contract，Contract 阶段不得早于所有消费者升级完成。API 弃用必须提供替代方案、遥测和截止版本；紧急安全删除除外，但仍需批准与通知。

## 6. 回滚与前滚

发布计划必须针对代码、配置、数据库、索引和模型分别说明恢复方式。不可逆数据迁移不能只写“回滚镜像”，必须先备份、验证恢复或设计补偿/前滚脚本。

## 7. 发布记录

使用 [`templates/RELEASE_RECORD.md`](../../templates/RELEASE_RECORD.md) 建立 `records/releases/<version>.md`。记录实际时间、制品摘要、环境、迁移、批准、测试/UAT、安全证据、观察指标、回滚状态和最终结论。
