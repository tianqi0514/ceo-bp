## 1. 验收目标

验收证明交付物在约定业务场景、数据、权限和运行条件下满足已批准标准。验收不是重复执行开发自测，也不以演示成功代替完整证据。

## 2. 验收范围

每个版本从以下类别中选择适用项并给出阈值：

- 功能：用户旅程、业务规则、导入导出、异常和边界；
- 数据：口径、对账、新鲜度、完整性、版本和可追溯性；
- 权限：角色、组织、租户、文档/切片、审批和审计；
- 分析：归因可解释、预测回测、区间、场景可重现；
- AI/知识：召回、引用、忠实度、拒答、提示注入和越权；
- 非功能：性能、容量、可用性、恢复、安全、可访问性；
- 运营：监控、告警、手册、备份、支持和培训；
- 交付物：源码、制品、SBOM、文档、测试、发布和已知问题。

## 3. 验收角色

- 业务验收负责人：批准范围、组织 UAT、签署结论；
- 业务用户：按真实场景执行并记录结果；
- 产品负责人：解释需求和验收标准，不代替业务签字；
- 测试负责人：准备环境/数据，汇总证据，保持结论独立；
- 开发负责人：定位修复问题，不自行改写 UAT 结果；
- 运维/安全/数据负责人：签署相应非功能和治理条目。

## 4. 验收前置条件

- 验收范围、标准、人员和日程已批准；
- 候选版本和配置冻结并唯一标识；
- 系统测试报告结论允许进入 UAT；
- 环境、数据、账号、权限和外部依赖准备完成；
- 已知问题、限制、回滚和支持渠道已披露；
- 验收用例能追溯到需求，预期结果已由业务确认。

## 5. 执行步骤

1. 启动会确认范围、版本、环境、数据截止点和证据方式；
2. 业务用户按用例执行，记录实际结果、时间和证据；
3. 失败项登记缺陷，不得仅口头说明“后续优化”；
4. 修复产生新候选版本后，重测失败项并执行受影响回归；
5. 汇总需求覆盖、通过率、缺陷、偏差和未测风险；
6. 相关责任角色分别签署业务、数据、安全和运维结论；
7. 验收负责人给出 Accepted、Conditionally Accepted 或 Rejected；
8. 条件验收项进入遗留清单，含责任人、期限和复验标准。

## 6. 建议验收场景

### 指标异常到决策复盘

业务用户发现目标偏差，验证指标口径和数据状态，完成下钻/贡献分析，引用文档证据，创建多个方案并审批，生成行动项，最后记录结果。全过程必须可从审计日志和决策档案重建。

### 知识权限

不同组织用户使用相同问题查询分级文档。结果只能引用各自有权版本；撤权或归档后，搜索、缓存、历史会话和导出均不得继续泄露正文。

### 预测可信度

对冻结历史数据执行预测，展示数据截止点、模型/参数、回测区间、基线对比、误差和置信区间；相同版本输入可重现结果，不能将 LLM 叙述当作数值验证。

### 故障与恢复

在批准环境模拟 worker、索引或上游查询不可用，验证超时、降级、重试、告警、用户提示和恢复，不产生重复决策/任务或数据丢失。

## 7. 验收判定

- `Accepted`：所有强制标准通过，无 Sev-1/2，遗留风险在阈值内；
- `Conditionally Accepted`：核心价值可用，无 Sev-1/2，少量偏差有书面责任人、期限和复验；
- `Rejected`：核心场景、数据正确性、权限、安全、恢复或强制标准不满足。

通过率不是唯一依据。一个跨租户泄露用例失败即足以拒绝验收。

## 8. 验收交付包

- 验收计划和用例；
- 候选版本、配置和数据标识；
- 需求追踪矩阵；
- 系统测试和安全/性能/恢复报告；
- UAT 实际结果与证据；
- 缺陷和遗留风险；
- 培训、用户和运维手册；
- 签署页与最终结论。
